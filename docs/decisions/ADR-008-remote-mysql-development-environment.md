# ADR-008：使用远程 Docker MySQL 作为共享开发与测试数据库

状态：Accepted
日期：2026-07-24
决策人：项目负责人

## 背景

项目需要在不同开发主机之间切换。每台主机分别维护本地 MySQL 会造成版本、配置、迁移状态和测试数据不一致。

项目已有一台可通过 SSH 访问且安装了 Docker 的远程服务器，因此需要确定统一开发与集成测试数据库的部署方式和安全边界。

## 决策

1. 开发和集成测试使用远程服务器中的 Docker MySQL。
2. 使用 Docker Compose 保存可重复执行的部署配置和操作命令。
3. 使用固定的 MySQL 8.4 LTS 补丁版本，不使用 `latest`。
4. MySQL 宿主机端口只绑定远程服务器的 `127.0.0.1`，不直接向公网开放 `3306`。
5. 服务器防火墙或安全组不得允许公网入站访问 MySQL 端口。
6. 开发主机默认通过使用密钥认证的 SSH 隧道连接远程 MySQL。
7. 开发库和集成测试库必须分离，并使用不同的非 root 最小权限账号。
8. 自动测试只能连接测试库，不得连接或清理开发库。
9. 数据库密码和服务器连接信息通过本地或服务器私有环境变量提供，Git 只保存 `.env.example`。
10. MySQL 使用持久化数据卷，并提供经过验证的备份和恢复流程。
11. 后续数据库结构变更统一通过 Flyway 管理，禁止在共享环境执行 `flyway clean`。
12. 该环境只用于开发和集成测试，不替代独立的生产数据库。
13. Collector 继续只通过 Information Hub 接入数据，不直接连接 MySQL。

## 备选方案

### 每台开发主机独立运行 MySQL

优点是可以离线开发，单台主机故障不会影响其他开发者。缺点是容易产生版本、迁移和测试数据差异，不符合当前跨主机共享环境的目标。

### MySQL 直接开放公网并启用 TLS

客户端连接步骤较少，但需要维护证书、来源 IP 白名单和公网攻击面。当前没有必须公网直连的需求，因此不采用。

### 建立 VPN 或专用网络

可以提供更完整的私网访问能力，但会引入新的网络基础设施和运维成本。当前阶段优先使用已有 SSH 能力。

## 正面影响

- 不同开发主机使用一致的 MySQL 版本和数据库环境。
- 数据库部署、启动和恢复过程可以文档化并重复执行。
- MySQL 不直接暴露公网，减少扫描和暴力破解风险。
- 开发库和测试库隔离，降低自动测试破坏开发数据的风险。

## 负面影响

- 远程服务器或网络不可用时，数据库集成测试会被阻塞。
- 多台开发主机共享环境时需要协调 Flyway 迁移版本。
- SSH 密钥、数据库账号和备份需要持续维护。
- 远程数据库延迟高于本地数据库。

## 重新评估条件

- 需要部署正式生产环境。
- CI 需要独立、可销毁的数据库环境。
- 开发人员或并行分支数量导致共享数据库频繁冲突。
- SSH 隧道不能满足网络性能或访问管理要求。
- 必须支持不经过 SSH 的公网或专用网络直连。
