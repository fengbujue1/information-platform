# ADR-010：Phase 2 建设标准化职位 Web 浏览 MVP

状态：Accepted
日期：2026-07-29
决策人：项目负责人

## 背景

Phase 1 已经完成职位采集、归档、快照和查询 API。

原路线图中的 Phase 2 包含职位浏览、搜索、详情、原始数据和历史版本查看。

当前 Job Query API V1 明确不返回 rawPayload，也没有读取端用户认证。如果为了原始数据查看而立即增加管理端权限、审计和脱敏接口，会明显扩大 Phase 2 范围。

## 决策

Phase 2 建设标准化职位 Web 浏览 MVP。

包含：

- 职位列表；
- 筛选、排序和分页；
- 职位详情；
- 历史快照；
- 通用页面状态；
- 前端测试；
- 受控构建和部署配置。

不包含：

- rawPayload；
- 用户系统；
- 复杂权限；
- 写操作；
- AI、推荐和通知；
- 公网无认证部署。

前端使用现有 Job Query API V1。列表筛选、排序和分页状态写入 URL Query；详情和快照页面使用经过校验的内部 `from` 参数恢复列表状态。快照只提供版本查看，不实现复杂 Diff。

开发环境通过 Vite Proxy 调用后端，部署环境优先使用 Nginx 同源反向代理，不在后端启用宽泛 CORS。

## 备选方案

### 方案一：Phase 2 同时建设管理端认证和 rawPayload

优点：

- 功能更完整。

缺点：

- 需要认证、授权、脱敏、审计和管理接口。
- 明显扩大 Phase 2。
- 更容易泄露来源原始字段。
- 延迟职位浏览 MVP。

### 方案二：直接公开无认证读取 API

优点：

- 部署简单。

缺点：

- 数据和接口直接暴露。
- 不符合当前受控开发阶段。
- 后续收紧访问会增加迁移成本。

### 方案三：只做标准化浏览 MVP

优点：

- 复用现有 API。
- 任务边界清晰。
- 最快形成可用界面。
- 安全风险较低。

缺点：

- 暂时不能查看 rawPayload。
- 暂时不支持多用户和公网访问。

## 结果

采用方案三。

## 正面影响

- Phase 2 可以在不修改数据库的情况下推进。
- 前后端契约清晰。
- 避免权限系统和 AI 提前进入。
- 可以快速验证职位浏览体验。

## 负面影响

- 当前 Web 只能在受控环境中使用。
- rawPayload 管理需要后续独立阶段。
- 公网部署需要额外认证任务。

## 重新评估条件

出现以下需求时重新评估：

- 需要多用户访问；
- 需要公网访问；
- 需要 rawPayload 管理；
- 需要职位收藏或备注；
- 需要管理 Collector；
- 需要查看敏感来源字段。
